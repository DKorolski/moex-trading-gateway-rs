3. Transaction, архив и replay

Создаётся immutable abort binding с hashes/bytes/custody исходных файлов и retained parent identities. Выбранные terminal timestamp/sequence фиксируются в create-once/fsynced intent; replay не вычисляет новый decision по текущим часам. reason_code связывает существующую terminal schema с canonical abort binding digest.

Pending и source копируются в fixed aborted evidence текущего manifest: исходные bytes и modes 0440/0400 сохраняются. Source не помещается в authority JSON с лимитом 128 КиБ. Архивирование использует bounded no-follow reads, descriptor-relative exclusive writes, fchmod/fchown, file/directory fsync и exact reread. Это допускает различные filesystems source и control root.

Только после проверки durable archives исходные files потребляются через retained parent descriptors и unlinkat; исходный inode удерживается открытым и проверяется. Рабочий .p1f-next освобождается, поэтому следующий source с новыми bytes не конфликтует со старой ошибкой. Parent substitution, links и foreign/partial archive не исправляются автоматически.

Затем переиспользуется terminal receipt → PHASE_TERMINAL event → head ordering. Единственный committed successor — EXPIRED/1/12; active manifest/deadline очищаются. Ready/O2_MATERIALIZED, промежуточная execution authority или sequence13 для второго terminal decision не создаются.

Private abort continuation распознаёт только свой exact intent/pending/frontier. Ordinary history/admission не получает permissive ignore-pending режима. До completion незавершённый abort блокирует normal inspect/admission/claim/materialization; после completion history проверяет receipt, binding и archive hashes/custody.

Lost-response replay возвращает прежние receipt/event/timestamp/sequence без новых эффектов. Отдельный fixture после завершения допускает future signed claim на sequence13; он не является новым operational O2 или bootstrap witness.

Важная честная граница: частично записанный archive после прерывания оставляет операцию fail-closed и исходный файл сохранённым. Автоматического ремонта такой partial copy нет. Это соответствует принятому контракту; не следует описывать реализацию как универсальное восстановление после любого возможного filesystem failure.
