3. P1-O3-R01: EXISTING PROOF НЕ ЗАВЕРШАЕТ FSYNC BOUNDARY

Файл:
crates/runtime-durable-service/src/stage8b_p1_semantic/observed/o3.rs

Существенные места:
- строка 56: existing-file ветвь;
- строка 58: retained::read и restore_pending;
- строка 70: write_all только в create ветви;
- строка 71: sync_all файла только в create ветви;
- строка 73: sync_all родительского каталога только в create ветви;
- строка 83: сравнение exact binding;
- строка 86: возврат permit без общего завершающего sync для existing branch.

Нормальный первый вызов соблюдает требование: proof записывается, файл и каталог синхронизируются, bytes перечитываются. Но восстановление уже существующего файла ограничивается чтением, проверкой canonical proof/freshness и binding.

Последовательность, нарушающая обещанный контракт:
1) первый процесс успел выполнить полный write_all proof;
2) процесс остановился до sync_all файла или до sync_all каталога;
3) новый процесс видит полные bytes и принимает existing-file ветвь;
4) permit возвращается без завершения синхронизации proof;
5) обычный путь сохраняет RequestAccepted в durable journal;
6) последующий OS/power crash может оставить journal с обязательным proof, который не был надёжно сохранён.

Обычный SIGKILL сам по себе не доказывает потерю файла: после него bytes обычно доступны через файловую систему/page cache. Дефект состоит в том, что повторный процесс принимает эти bytes и переходит через journal frontier, не восстановив требуемую durability boundary. Воспроизведение реальной потери после power failure в этом review не заявляется.

Production chain после возврата permit:
- stage8b_p1_semantic/redis.rs:1461, process_claimed_ready;
- recovery.rs:3935, commit_stage8b_p1_semantic_o3;
- crates/strategy-runtime-core/src/stage6d_live_core.rs:4018, append RequestAccepted.

На этом пути дополнительного fsync proof перед append нет. Proof расположен в configured durable_parent, journal/seal — внутри runtime root. Синхронизация других файлов не является контрактом сохранности этого proof. Последующий S1 содержит full proof, но не закрывает промежуточное состояние RequestAccepted-before-S1 — именно для него и требуется sidecar.

Это P1 относительно явного обязательства ТЗ «exact evidence durable до RequestAccepted». Ошибка ведёт к невозможности exact recovery и fail-closed остановке; автоматическая неверная заявка или двойной provider effect этим замечанием не доказаны.

Минимальная коррекция:
- после успешной canonical/freshness/exact-binding проверки существующего proof синхронизировать сам проверенный regular file, открытый с no-follow;
- синхронизировать его parent directory;
- перечитать/сверить exact bytes и лишь затем вернуть permit;
- при ошибке любого sync/reread вернуть отказ до callback/RequestAccepted;
- bytes, issued/checked/expires, phase и logical identity не переписывать, expired proof не обновлять.

Можно использовать небольшой общий завершающий участок для create и existing ветвей либо существующий локальный паттерн. Пример уже есть в stage8b_p1_semantic/observed/retained.rs:105: idempotent retry также выполняет file sync, parent sync и exact reread. Не нужно менять весь custody/storage layer.

Текущий тест redis/tests/observed/o3_readmission.rs:201 завершает первый fresh() успешно и только затем моделирует pre-append crash. Поэтому он не достигает внутренней границы write_all-before-sync.

Достаточное целевое доказательство исправления:
- остановить запись после полного proof write, но до завершения file/parent sync;
- повторно открыть ту же ещё свежую попытку;
- подтвердить порядок: file sync → parent sync → exact reread → callback/RequestAccepted;
- по отдельности инжектировать ошибку file sync и parent sync в existing-file ветви;
- при каждой ошибке journal/seal неизменны, callbacks/publication/provider/XACK отсутствуют, pending source не удалён;
- отсутствует mutation/reissue старого proof.

Инструментированного barrier/fault теста этой границы достаточно; новый стенд power-failure или полный recovery framework не требуется. Прежние source/replay witnesses остаются полезными и не обнуляются.

5. НЕБЛОКИРУЮЩЕЕ P2 УТОЧНЕНИЕ COVERAGE

Текущий документ говорит «omitted day unknown and fails closed». Код проверяет coverage только после model-session classification:
hybrid_intraday_runtime/session_catchup.rs:95 и :101.

При frozen weekends_off=true weekend bars получают WeekendSuppressed и проходят continue до coverage.contains. Поэтому Friday 2026-10-09T16:50Z → Monday 2026-10-12T07:10Z при coverage только 9 и 12 октября может пройти без explicit empty sessions 10 и 11 октября. Distance меньше four-day resource bound; endpoint checks не обнаруживают отсутствующие даты.

Это не новый торговый риск и не P1: отсутствие weekend callbacks следует из уже фиксированного правила модели; исторические заявки не создаются. Но текст контракта шире фактической проверки.

Минимально нужно выбрать и зафиксировать одну трактовку: либо требовать explicit empty weekend sessions и проверять date presence до model suppression, либо прямо описать допустимость пропуска модельно запрещённых выходных при frozen weekends_off. Предпочтительно уточнить существующее правило без изменения frozen model. Holiday/clearing и неизвестные интервалы регулярной модельной сессии по-прежнему не должны выводиться из отсутствующих bars. Новый календарный механизм не нужен.

7. МИНИМАЛЬНЫЙ ОСТАТОК ДО PAPER → LIVE MICRO

Поддерживаю исходную цель: несколько paper-сессий с сопоставлением ALOR, затем live micro. В этом review не предлагаю расширять её общей платформой, многомесячным soak или возвратом обязательного High180/LB120.

Нынешний целевой профиль — IMOEXF baseline07 BO-only/no-riskgate согласно принятому ADR от 30 сентября. Candidate09 остаётся отдельной моделью. MR и riskgate не возвращаются в критический путь этого профиля. Будущие USDRUBF/RI проверяются позже по своим контрактам.

Рекомендуемая последовательность без новых macro-stages:

А. Закрыть одну fsync correction и узкий source re-review; уточнить P2 в том же комплекте документации.
Б. Собрать один final release/authority/install artifact с новым exact plan, включая catchup_coverage, и сохранением O2 root/history. Qualification final binary выполнить в рамках этого artifact, без нового design-only цикла.
В. Выполнить существующий bounded O3 на установленном контуре: fresh admission/catch-up → один обычный paper lifecycle → restart/replay → bounded stop, с сохранённым P0 и объяснимым итоговым PEL/journal/seals. Операционные строки нельзя закрывать только локальными fixture тестами; применимые ранее принятые проверки можно ссылочно переиспользовать.
Г. O4 и несколько paper-сессий на реальных FINAM данных с параллельным frozen ALOR comparison. Проверки данных, reconnect/REST overlap, freshness и EOD включить в эти же сессии.
Д. При выполнении измеримых критериев — отдельный допуск выбранного профиля к live micro с минимальным объёмом, одним владельцем и понятной процедурой остановки/reconciliation.

Практический ориентир — 3–5 paper-сессий; это ориентир объёма наблюдения, а не новое обязательное календарное правило. Важнее наличие полезных сигналов, хотя бы одного полного lifecycle и проверенного перехода сессии/рестарта. Если спокойные дни не дают этих событий, время наблюдения само по себе их не доказывает: редкие границы закрываются существующими целевыми тестами, а не бесконечным ожиданием.

Минимальный критерий выхода из paper:
- один и тот же frozen model/profile, timezone/session labels и необходимый warmup;
- совпадающие либо объяснимо различающиеся M10 inputs; нет необъяснённых пропусков, сдвигов на бар и повторов;
- все различия ALOR/FINAM decisions разобраны по конкретным барам; сравнение цены fill/PnL не подменяет сравнение сигналов;
- virtual orders/fills/position/fees и EOD объясняются journal, нет неучтённого pending или unknown outcome;
- restart/reconnect сохраняют состояние и не дают повторного эффекта; readiness/freshness действительно снимают новые входы при отказе;
- native final binary, единственный execution owner, допустимый объём/лимиты и broker capabilities соответствуют профилю первого micro;
- нет открытого P1, влияющего на первый live route.

Для первого micro достаточно narrow supported route этого профиля. Stops/brackets или функции других стратегий не должны задерживать его, если первый профиль ими не пользуется и это явно закреплено его разрешёнными возможностями. Если профиль зависит от конкретной защиты, её корректность, напротив, входит в обязательный допуск.

Простой rollback контейнера при реальных ордерах недостаточен: остановка новых входов, установление единственного владельца и reconciliation реальной позиции/активных заявок должны быть понятны оператору. Это эксплуатационный критерий первого micro, а не требование разрабатывать новую универсальную систему.

8. ЧТО ПЕРЕДАТЬ ПРОГРАММИСТУ СЕЙЧАС

Сохранить прежние successful и failed logs с честной привязкой к версиям.

После этого — точечный re-review дельты и переход к уже предусмотренным release/O3/O4 шагам. Других новых source blockers в проверенном scope не обнаружено.
