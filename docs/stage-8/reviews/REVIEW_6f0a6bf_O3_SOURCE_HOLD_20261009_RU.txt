1. P1-O301 — ранний SIGTERM/SIGINT может запустить runtime без shutdown intent

Место:
crates/finam-gateway/src/stage8b_p1f_o3_composition.rs, run_fixed,
строки 113–124: создание lazy runtime future и две signal-ветви второго select.
crates/runtime-durable-service/src/stage8b_p1e_process.rs:
execute_stage8b_p1e_observed_run_v1, строки 4518–4526;
execute_run_with_observed_window, строки 5234–5258.

Суть: composition подписывается на SIGTERM/SIGINT до подготовки Published window.
Внутренний runtime создаёт собственные signal receivers позднее, при выполнении
своего async entrypoint. Получив сигнал во втором select, composition устанавливает
stop только для schedule publisher и затем вызывает runtime.await. Это await может
впервые запустить runtime, уже после получения и обработки внешнего stop.
В существующий runtime latch/coordinator обработанный stop не передаётся.

Допустимое расписание, непосредственно следующее из кода:

  1) Published window готов; первая стадия select завершена.
  2) Внешний SIGTERM либо SIGINT доставлен ранее подписанному composition receiver.
  3) Второй biased select выбирает signal-ветвь прежде первого poll runtime future.
  4) stop.send(true) останавливает producer; runtime.await запускает runtime.
  5) Runtime загружает config, создаёт новые signal receivers и новый clear latch.
     Ранее доставленный сигнал не превращается в retained shutdown intent.
  6) Runtime может пройти admission и обработать уже подготовленные M10/свежий
     signed schedule. Затем он может ждать без запроса штатного drain, пока
     внешний guardian не применит свой force-kill backstop.

Аналогичная щель есть во время синхронной загрузки config до регистрации внутренних
receivers: первый poll сам по себе не доказывает, что runtime уже подписан на stop.
Отзыв signer authority не отменяет ранее опубликованные подписанные данные.
Поэтому сохранность guardian deadline и SIGKILL recovery не устраняет возможность
новой обработки после уже принятой команды остановки.

Это статически установленный дефект handoff/control flow. Rust/Tokio процессное
воспроизведение в среде reviewer не выполнялось: Rust/Cargo/Docker отсутствуют.
Run7 останавливает уже работающий, восстановленный runtime и этой щели не проверяет.

Механика подписки сверена с первичными материалами Tokio: Signal создаёт отдельного
listener; registry использует watch::Sender::subscribe; новая подписка считает
предшествующие сообщения уже увиденными. Ссылки на публичный контракт и исходники:
https://docs.rs/tokio/latest/src/tokio/signal/unix.rs.html
https://docs.rs/tokio/latest/src/tokio/signal/registry.rs.html
https://docs.rs/tokio/latest/tokio/sync/watch/struct.Sender.html#method.subscribe
В submitted Cargo.lock закреплён Tokio 1.52.3. Исполнение этой зависимости здесь
не заявляется; regression должен использовать закреплённую версию проекта.

Минимальная коррекция:

  • Обеспечить непрерывную передачу уже замеченного shutdown в существующий
    runtime coordinator/latch до startup/admission либо сохранить достаточную
    раннюю signal subscription при handoff. Выбор небольшого source seam — за
    программистом; новые authority/roles/control-root механизмы не нужны.
  • Stop до старта runtime не должен запускать fresh admission/callback/effects.
    Для runtime, уже владеющего durable owner, сохранить обычный bounded drain;
    отменять/drop pending durable future ради быстрой остановки нельзя.
  • Сохранить first-wins cause, исходные deadline/grace и fatal exit precedence.
    Разовый повторный raise до поздней подписки не обеспечивает передачу intent.

Достаточное evidence для закрытия P1-O301:

  • Детерминированная граница после получения Published window и до внутреннего
    startup/signal admission. Реальные SIGTERM и SIGINT, каждый отдельным case;
    подтвердить, что stop уже принят composition до release barrier.
  • На stop-before-start: zero fresh runtime admission/callback/provider/command
    publication/XACK; неизменные durable root/journal и bootstrap marker/receipt
    O2. Уже опубликованные producer данные сохраняются для recovery, без reset.
  • No-signal control запускает обычный runtime. Прежний положительный
    Market → successor → restart → stop witness остаётся положительным.
  • Контроль без correction должен отклоняться этим regression; не использовать
    timing sleep, table lookup или проверку только итогового force-kill.
  • Сохранить exact selectors, raw logs/exit codes и source binding. Достаточны
    focused Linux/process regressions и обычные checks затронутых модулей.

Не требуется повторно разрабатывать I1 supervision, весь guardian, новую систему
сигналов или все исторические crash-frontiers.
