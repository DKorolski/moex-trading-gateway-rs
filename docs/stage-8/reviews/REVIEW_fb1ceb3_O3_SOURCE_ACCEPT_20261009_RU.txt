1. Почему P1-O301 закрыт

Проверена узкая дельта относительно предыдущего review: четыре изменённых Rust
файла и один новый cfg(test) модуль; остальные изменения — runner/checker/docs.
Всего tracked delta: 11 changed, 4 added, 0 deleted. Cargo/Cargo.lock, workflows,
deploy templates и config-файлы не менялись; strategy-runtime-core не изменён.

В run_fixed общий Stage8bP1eCoordinatorV1/latch создаётся до lazy runtime future.
После принятия SIGTERM либо SIGINT composition сохраняет ExternalSignal в этом
latch и ожидает тот же runtime future. Ранее обработанный stop больше не зависит
от того, когда runtime создаст собственные Unix signal receivers.

execute_stage8b_p1e_observed_run_with_shutdown_v1 получает тот же coordinator:
проверяет retained stop до загрузки config и повторно до owner startup.
Owner task и обычный supervisor используют его же Arc/latch. Preset stop
отклоняется до admission; существующий durable future при позднем stop не
отменяется и не подменяется новым owner.

Grace берётся из уже validated config. OnceLock сохраняет первую cause, sequence
и deadline; supervision при RetainedIntent использует сохранённый deadline.
Повторный сигнал не продлевает grace. Неожиданный выход publisher сохраняет
OwnerFailure и остаётся fatal Producer error; ненадёжный pre-subscription raise
удалён. Унаследованный bounded drain и fatal owner-panic precedence сохранены.

Ранний stop до аутентифицированного owner даёт DurableRestart / runtime exit
class 66. Это консервативный отказ до admission, не authenticated exit 0.
В положительных process-тестах OS exit оболочки равен 0, поскольку оболочка
проверяет именно ожидаемый runtime error 66. Документация различает эти значения.

2. Signal cases и отрицательные controls

Изучены сам Rust harness, Python runner и raw logs. cfg(test)-only Unix datagram
barrier стоит после реальной typed Published pair и до внутреннего startup.
Nonroot child выполняет настоящий run_fixed, а parent отправляет реальный OS
signal. Порядок задаётся событиями, а не sleep:
PUBLISHED_WINDOW_READY → STOP_ACCEPTED → RELEASE → RUNTIME_RELEASED.

Проверенные retained cases:

  SIGTERM-retained: harness exit 0; child test exit 0; runtime error class 66.
  SIGINT-retained:  harness exit 0; child test exit 0; runtime error class 66.

В обоих случаях STOP_ACCEPTED предшествует RUNTIME_RELEASED; retained cause —
ExternalSignal, first_sequence=1. До/после совпадают durable root/journal/seal,
bootstrap transaction/receipt, M10/command rows и group states. Реальные Redis
commandstats XREADGROUP/XAUTOCLAIM/XACK остаются 0; producer checkpoint не сброшен.
Zero admission следует также из guard до config/root loading, а не только из
сохранённого boolean PASS. Нет callback/provider/command effect или force-kill.

Отрицательные controls для SIGTERM и SIGINT отключают только запись в latch.
Оба child завершаются exit 101 с точной диагностикой:
P1-O301: stop accepted without retained runtime intent.
Parent harness exit 0 означает успешное обнаружение отрицательного сценария.

Граница отрицательного доказательства прозрачна: assertion обнаруживает
отсутствующий intent до release/runtime startup. Это не заявленное исполнение
опасных paper effects старой версии. Для этой узкой коррекции такой control,
положительные zero-effect cases и отдельно квалифицированный обычный runtime
дают достаточное evidence. Test barrier/mutation switch не входят в production.
